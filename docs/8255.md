# 8255 PPI interface

## Mapping (unchanged from the original program)

| Port | Address | Use |
|---|---|---|
| A | 80H | **PA0 GREEN, PA1 YELLOW, PA2 RED** |
| B | 82H | *(new, optional)* PB0 LEFT, PB1 STRAIGHT, PB2 RIGHT arrows |
| C | 84H | unused |
| Control | 86H | `80H` = mode 0, ports A, B, C all outputs |

| State | Port A |
|---|---|
| GREEN | `001b` = 01H |
| YELLOW | `010b` = 02H |
| RED | `100b` = 04H |
| OFF | 00H |

Control word `80H` = `1000 0000b`: bit 7 = 1 (mode set), group A/B mode 0, A/B/C
outputs. This is exactly what the original `MOV DX,86H / MOV AL,80H / OUT DX,AL` did.

## Where it lives

* Assembly: `platform/dos/hw/hw8255.inc` - the **only** file with port numbers.
  `HW_Init`, `HW_Apply` (reads `te_state`/`te_dir`), `HW_Shutdown`.
* C++: `hardware/i8255_backend.*` (talks to a `PortIO`; `Simulated8255` for tests,
  `DevPortIO` for `/dev/port` on Linux).
* JS: `I8255Backend` in `platform/desktop/js/hardware.js` (virtual chip; the log pane
  shows `OUT 80H, 02H` lines).

The engine never sees these numbers: `TrafficEngine -> HardwareInterface -> I8255Backend -> OUT`.

## Availability probe

In mode 0 a real 8255 returns the output latch when read. `initialize()` writes `A5H`
to Port A and reads it back; a missing chip floats the bus (`FFH`) and the backend
reports "unavailable", so `selectHardware` can fall back to simulation. The DOS
program records the result (`hw_present`, shown as `OUT: 8255` / `SCREEN ONLY`) but
**still sends the OUTs**, like the original, so DOSBox setups that capture OUT but do
not answer IN keep working.

## Cautions

* On an ordinary PC, ports 80H-8FH are **not** an 8255 (80H is the POST-code port,
  81H-8FH are DMA page registers). Run on real ports only with an 8255 trainer
  / card that you know is decoded there. `DevPortIO` needs root and is opt-in.
* Outputs are driven straight from the 8255 pins; use buffers/drivers (e.g. ULN2003
  or transistors) and current-limit resistors for LEDs.
